Introducing XTJSON

A syntactic superset of JSON for files that are written and maintained by people.

Specification draft {{DRAFT}} · {{DATE}} · Specification (English) · Spezifikation (Deutsch) · GitHub

XTJSON is a notation for JSON data that is comfortable to write by hand. It is meant for files that people edit, such as configuration files. It extends only the notation of JSON. The data model stays exactly that of JSON: object, array, string, number, true, false and null.

Every UTF-8 encoded JSON text is a valid XTJSON document with the same meaning, and every XTJSON document has a JSON equivalent that determines its value. XTJSON has no new data types, no expressions and no references. It is not an interchange format between machines; for that purpose JSON remains the format of choice.

XTJSON documents are encoded in UTF-8. The recommended file extensions are .xtjson and .xtj.

What XTJSON adds to JSON

  • Comments: // …, # … and /* … */.
  • Names without quotation marks: port: 8080.
  • Line breaks as separators: a line break can take the place of a comma.
  • Trailing commas in objects and arrays.
  • Optional braces around the object at the top level.
  • Strings in single quotation marks: '…'.
  • Strings across several lines, with the indentation removed, and line continuation with \.
  • More escape sequences: \', \v, \0, \xHH and \u{…}.
  • Hexadecimal, octal and binary integers: 0xFF, 0o755, 0b1010.
  • Digit grouping with _: 1_000_000.
  • Number suffixes: 10k, 64mb, 250ms.
  • Named values: identifiers that the application defines as aliases for JSON values, such as nil.
  • More white space characters: all white space characters of ECMAScript.

The forms of XTJSON

The diagrams below show the notation. Boxes with round ends are characters to be written literally, rectangular boxes refer to another diagram, and boxes with a dashed border describe a set of characters. White space and comments may appear between any two tokens; the diagrams leave them out, except in the separator, where a line break matters.

document

A document is either a single value, as in JSON, or a sequence of members without enclosing braces. The second form denotes the object that contains exactly these members and needs at least one member. It exists only at the top level; an empty object is written as {}.

{{rr:document}}

object

An object is an unordered set of name/value pairs. It begins with { and ends with }. If a name occurs more than once, the member that comes last in the document applies.

{{rr:object}}

members

Each member is a name followed by : and a value. Members are separated by a separator. After the last member there may be exactly one trailing comma, which has no meaning.

{{rr:members}}

array

An array is an ordered collection of values. It begins with [ and ends with ]. Values are separated by a separator; a single trailing comma is allowed.

{{rr:array}}

separator

Two consecutive items are separated by exactly one comma, or by white space that contains at least one line break outside block comments. A comma together with line breaks is fine. Two items on the same line without a comma are an error, and so are two commas in a row.

{{rr:separator}}

value

A value can be an object, an array, a string, a number or a named value. These structures can be nested.

{{rr:value}}

named value

A named value is an identifier at a value position. It is another notation for the JSON value that a definition assigns to it. true, false and null are predefined and cannot be changed. The application can pass further definitions to the parser, for example nil for null; the assigned value is a string, a number, true, false or null, never an object or an array. A document cannot define named values itself, case is significant, and an identifier without a definition is an error; it is never read as a string.

{{rr:named value}}

name

A name is a string or an identifier. The notation does not matter for the identity of a name: a, "a" and 'a' denote the same name. At a name position an identifier is always a name, so {null: null} has the name "null".

{{rr:name}}

identifier

An identifier begins with an ASCII letter, _ or $, followed by any number of ASCII letters, ASCII digits, _ or $. Every other name must be written in quotation marks, for example names with spaces, hyphens, dots or non-ASCII characters.

{{rr:identifier}}

string

A string is a sequence of zero or more Unicode characters, enclosed in double or in single quotation marks; both forms are equivalent. A string may extend across several lines: line breaks and tabs may appear in it unescaped. The delimiter, the backslash and all other control characters, including vertical tab and form feed, must be written as an escape.

{{rr:string}}

A string without a line break has the same value as in JSON. For a string across several lines, the value is obtained in four steps:

  1. The text is split into lines at every line break, including the line break of a line continuation (\ before a line break).
  2. Unescaped spaces and tabs at the end of every line except the last are removed. A line that ends with a line continuation keeps the white space before the \.
  3. If the string begins with an empty line, that line is dropped and the smallest indentation of all non-empty lines is removed from every line. The last line always counts, so the position of the closing delimiter helps determine how much is removed. The removed characters must be the same in all lines; mixing tabs and spaces there is an error.
  4. The lines are joined with a line feed (U+000A), then the escape sequences are resolved. A line continuation drops its \ together with the line feed, so the indentation of the continued line is removed, but no line break remains.

escape

XTJSON has all escape sequences of JSON and six more from ECMAScript: \', \v, \0, \xHH, \u{…} and the line continuation, a backslash directly before a line break, which yields nothing. They apply in both string forms. \u{…} stands for a code point up to 10FFFF outside the surrogate range. Every other sequence that begins with a backslash is an error, including a backslash before a space or tab.

{{rr:escape}}

number

A number is a decimal number as in JSON or an integer in hexadecimal, octal or binary notation, optionally with a minus sign in front and a suffix directly behind. White space inside a number is an error.

{{rr:number}}

decimal

Without _ this is exactly the number grammar of JSON: an integer part, an optional fraction part and an optional exponent. Leading zeros such as 0755, a leading + and a missing integer or fraction part (.5, 5.) remain errors.

{{rr:decimal}}

digits

Between two digits there may be exactly one _. It has no meaning and is discarded when reading. This holds for every digit sequence, including the digits of hexadecimal, octal and binary integers.

{{rr:digits}}

integer

Integers can be written in hexadecimal (0x), octal (0o) or binary (0b) notation. Case does not matter in the prefix or in the hexadecimal digits. These forms have no fraction part and no exponent. Their value is exact: an implementation that cannot represent it reports an error and never rounds.

{{rr:integer}}

suffix

A suffix directly after the last digit stands for a conversion that turns the number into another number. It consists of the same characters as an identifier, but cannot begin with _. Case is significant and the longest match applies.

{{rr:suffix}}

The first character cannot be a to f, o or x in either case, and it cannot be _, so a suffix is never confused with a hexadecimal digit, an exponent, a number prefix or digit grouping.

All suffixes are predefined and cannot be changed; the application cannot add any. A suffix that is not in this table is an error:

white space

White space can be inserted between any pair of tokens. The white space characters are the four of JSON (space, tab, line feed, carriage return) and all further white space characters of ECMAScript, among them the no-break space and the byte order mark. A comment counts as white space.

{{rr:white space}}

comment

A line comment begins with // or # and extends up to the next line break or to the end of the document. A block comment begins with /* and ends at the first */ that follows; block comments cannot be nested. A line break inside a block comment is not a separator.

{{rr:comment}}

line break

A line break is a line feed, a carriage return, or the sequence of both, which counts as a single line break. In a string it becomes a line feed. All other white space characters, including U+2028 and U+2029, are not line breaks: they neither separate items nor end a line comment.

{{rr:line break}}

From XTJSON to JSON

The meaning of a document is defined by its JSON equivalent, which is obtained as follows:

  1. Comments are removed, and white space characters that JSON does not have become spaces.
  2. The members of an implicit root object are enclosed in { and }.
  3. Exactly one comma is put between two consecutive items; trailing commas are dropped.
  4. An identifier at a name position becomes the JSON string with the same characters.
  5. Strings become JSON strings in double quotation marks with the same value.
  6. Numbers are written as JSON numbers: without _, in decimal notation, and with the suffix replaced by the result of its conversion.
  7. Named values other than true, false and null are replaced by the JSON value assigned to them.

A document that uses at least one of the extensions is not a JSON text. It must not be labelled with the media type application/json or sent to recipients that expect JSON.

Principles

  • Definitions belong to the parser, not to the document. A document can define neither named values nor suffixes. Named values can be defined by the application; suffixes are fixed by the specification. A document that uses only the predefined named values is portable: every conforming parser can read it.
  • Errors instead of guessing. Unknown escape sequences, white space after a line continuation, undefined identifiers, unknown suffixes and mixed indentation are errors and are not silently interpreted.
  • Never code. XTJSON is not a subset of a programming language and is never read by evaluating it as program code.

Specification and implementations

The specification is the source of truth. It is available in English and German; both versions are equal in rank. This page is an informal overview. Where it differs from the specification, the specification applies.

The reference parser in the repository is written in Python. It makes the specification testable and comes with the test cases that serve as the conformance corpus for implementations.
